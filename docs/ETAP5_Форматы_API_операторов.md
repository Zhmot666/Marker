# Этап 5: Форматы API операторов маркировки

Реализация форматов запросов и ответов API по операторам (приоритет: Казахстан, Узбекистан). Без БСП.

**Документация по Казахстану (СУЗ-Облако, ismet):** `Для работы (временная)/Documentation/ismet/API.pdf` — руководство программиста API 2.0 (эмиссия КМ, отчёты, проверка доступности и др.).

---

## 1. Проверка доступности сервера перед запросом (ping)

**Требование:** перед каждым обращением к API оператора (заказ кодов, отчёты и т.д.) выполнять проверку доступности сервера — **GET-запрос (ping)**. Если ping завершился ошибкой (нет ответа, код не 200), основной запрос (POST и т.д.) не выполнять; запись очереди оставить на повтор или зафиксировать ошибку.

**Место реализации:** в **ОчередьОбменаМаркировкиСервер**, в процедуре обработки записи очереди — перед вызовом `HTTPКлиентМаркировкиСервер.ВыполнитьЗапрос` для основного метода:
1. Сформировать URL и заголовки для ping по правилам оператора (см. ниже по странам).
2. Выполнить GET ping.
3. Если результат неуспешен — обновить статус записи очереди (ошибка/повтор), записать в лог, выйти без отправки основного запроса.
4. Если ping успешен — выполнять основной запрос как сейчас.

Для **Казахстан (API СУЗ, документация ismet):** метод «Проверить доступность СУЗ» (п. 4.4.12):
- **Метод:** GET.
- **URL:** `{базовыйURL}/api/v2/{extension}/ping?omsId={omsId}`  
  Пример для фармы: `GET /api/v2/pharma/ping?omsId=CDF12109-10D3-11E6-8B6F-0050569977A1`
- **Заголовки:** `clientToken` (маркер безопасности), при необходимости `Accept: application/json`.
- **Параметр `omsId`** — уникальный идентификатор СУЗ (берётся из настроек/справочника оператора; в документации указано, что доступен в настройках СУЗ).
- **Ответ при успехе:** HTTP 200, тело JSON с полем `omsId`.

Путь для ping по товарной группе тот же `extension`, что и для заказа: фарма — `pharma`, молоко — `milk`, табак — `tobacco`, алкоголь — `alcohol`, обувь — `shoes`, вода — `water`, одежда и т.д. — `lp`. В 1С брать из **ТипыПродукцииМаркировки.ОбозначениеТоварнойГруппы** или задать в модуле форматов соответствие страна/тип → extension для ping.

Если у оператора (Узбекистан и др.) в документации описан иной способ проверки доступности — реализовать по его спецификации; при отсутствии метода — на усмотрение (можно пропускать ping для данной страны или использовать общий GET базового URL).

## 2. Цель этапа

- **Запрос «Заказ кодов»:** формировать тело HTTP-запроса (JSON) по формату оператора и подставлять корректный путь к методу API.
- **Ответ «Заказ кодов»:** разбирать ответ API (JSON или бинарный), извлекать коды по строкам заказа, заполнять документ **ПоступлениеКодовМаркировки** (шапка + ТЧ «Коды») и при проведении — регистр **КодыМаркировки**.

Форматы берутся из официальной документации операторов и при необходимости из примеров (в т.ч. Python).

## 4. Данные для формирования запроса заказа кодов

Источники:

- **Документ ЗаказКодовМаркировки:** Заказ (ссылка), ТЧ Коды: Номенклатура, КоличествоЗаказа, КоличествоКодов.
- **Справочник Номенклатура:** ТипПродукции, GTIN (13).
- **Справочник ТипыПродукцииМаркировки:** ОбозначениеТоварнойГруппы (для пути API, например `pharma`).
- **Документ Заказ:** Контрагент.
- **Справочник Контрагенты:** ИНН, Страна (для выбора оператора и при необходимости для тела запроса).

По каждой строке заказа кодов в тело запроса обычно передаются: идентификатор товара (GTIN), тип продукции или товарная группа, количество кодов. Точная структура JSON — по документации оператора (Казахстан, Узбекистан).

## 5. Структура реализации по странам

Рекомендуется вынести форматы в отдельный общий модуль (серверный), чтобы не раздувать модуль очереди.

### 5.1. Общий модуль «ФорматыAPIМаркировкиСервер» (создаётся вручную)

Содержит:

- **ФормироватьТелоЗапросаЗаказКодов(Страна, ДокументЗаказКодов)** — возвращает строку JSON для тела POST-запроса. Внутри: выбор формата по Страна, чтение документа и ТЧ, обход строк, подстановка GTIN, типа продукции, количества и т.д. по формату оператора.
- **ПолучитьПутьAPIЗаказКодов(Страна, ОбозначениеТоварнойГруппы)** — возвращает путь к методу заказа кодов (например `/api/v2/pharma/orders`). Параметры по необходимости; если путь единый — ОбозначениеТоварнойГруппы может не использоваться.
- **ПолучитьПутьPing(Страна, ОбозначениеТоварнойГруппы)** — возвращает путь для проверки доступности (например `/api/v2/pharma/ping`). Для Казахстана — по документации СУЗ (п. 4.4.12). Параметр omsId добавляется в строку запроса при формировании URL в вызывающем коде (значение брать из настроек оператора/справочника).
- **РазобратьОтветЗаказКодов(Страна, ТелоОтветаБинарный, ДокументЗаказКодов)** — разбор ответа, возврат структуры для заполнения документа ПоступлениеКодовМаркировки: массив строк ТЧ (Номенклатура, НомерСтрокиЗаказа, Количество, СмещениеВОтвете при необходимости), общее КоличествоКодов, при необходимости список кодов/смещений для последующей записи в регистр при проведении. Либо процедура сразу заполняет переданный объект документа и вызывающий код только записывает/проводит.

Имена и сигнатуры можно уточнить под выбранную схему (возврат структуры или заполнение документа).

### 5.2. Интеграция в существующий код

- **В форме/модуле документа ЗаказКодовМаркировки** (при постановке в очередь):  
  ТелоЗапроса = ФорматыAPIМаркировкиСервер.ФормироватьТелоЗапросаЗаказКодов(Страна, ЭтаСсылка);  
  ОчередьОбменаМаркировкиСервер.ДобавитьВОчередь(Перечисления.ТипОперацииОчередиМаркировки.ЗаказКодов, ТелоЗапроса, ЭтаСсылка).  
  Страна брать из Заказ.Контрагент.Страна.

- **В ОчередьОбменаМаркировкиСервер**, перед основным запросом:  
  Сформировать URL для ping: базовый URL + ПолучитьПутьPing(Страна, ОбозначениеТоварнойГруппы) + при необходимости параметры (например `?omsId=...` для Казахстана). Выполнить GET ping; при неуспехе — не выполнять основной запрос, обновить статус очереди и выйти.

- **В ОчередьОбменаМаркировкиСервер**, при формировании URL для основного запроса:  
  Путь = ФорматыAPIМаркировкиСервер.ПолучитьПутьAPIЗаказКодов(Страна, ОбозначениеТоварнойГруппы);  
  ПолныйURL = ОбъединитьПутьURL(URL, Путь) или аналог. ОбозначениеТоварнойГруппы при необходимости брать из первой строки заказа (Номенклатура.ТипПродукции.ОбозначениеТоварнойГруппы) или по правилам оператора.

- **В ОчередьОбменаМаркировкиСервер**, в **СоздатьПоступлениеКодов**:  
  Вызвать ФорматыAPIМаркировкиСервер.РазобратьОтветЗаказКодов(Страна, ТелоОтветаБинарный, ДокументЗаказКодов) и по результату заполнить шапку и ТЧ созданного документа ПоступлениеКодовМаркировки, затем Записать(Проведение). Либо передать в РазобратьОтветЗаказКодов уже созданный объект документа для заполнения.

- **В документе ПоступлениеКодовМаркировки**, при проведении:  
  Формирование записей регистра **КодыМаркировки** по ТЧ «Коды» и при необходимости по разобранным данным (коды из ОтветAPIБинарный по СмещениеВОтвете/НомерВОтвете) — либо логика уже в модуле проведения, либо вспомогательная функция в ФорматыAPIМаркировкиСервер/в модуле документа.

## 6. Казахстан

- Документация: **СУЗ-Облако 3.1**, руководство программиста API 2.0 — файл `Для работы (временная)/Documentation/ismet/API.pdf`. URL стендов: тест — https://suzcloud.stage.ismet.kz/, продуктивный — https://omscloud.ismet.kz/.
- **Проверка доступности (обязательно перед каждым запросом):** метод «Проверить доступность СУЗ» (п. 4.4.12): **GET** `{базовыйURL}/api/v2/{extension}/ping?omsId={omsId}`, заголовок `clientToken`. Для фармы: `GET /api/v2/pharma/ping?omsId=...`. Идентификатор СУЗ `omsId` — из настроек/документации оператора (в справочнике операторов можно завести реквизит или хранить в настройках).
- В **ПолучитьПутьPing** для Казахстана возвращать путь вида `/api/v2/pharma/ping` (extension по типу продукции: pharma, milk, tobacco, alcohol, shoes, water, lp).
- В **ФормироватьТелоЗапросаЗаказКодов** при Страна = Казахстан формировать JSON по спецификации из API.pdf (заказ: products с gtin, quantity, serialNumberType, templateId и т.д., п. 4.4.1; для фармы — factoryId, factoryName, releaseMethodType, country и др.).
- В **ПолучитьПутьAPIЗаказКодов** для Казахстана возвращать путь из документации (например `/api/v2/pharma/orders` с параметром omsId в строке запроса).
- В **РазобратьОтветЗаказКодов** для Казахстана разбирать ответ (JSON), сопоставлять коды со строками заказа, формировать данные для ТЧ и для регистра.

## 9. Порядок выполнения (Этап 5)

1. Изучить документацию API операторов Казахстана и Узбекистана (п. 1 — проверка доступности; методы заказа кодов, примеры запроса/ответа). Для Казахстана — `Documentation/ismet/API.pdf`.
2. Создать общий модуль **ФорматыAPIМаркировкиСервер** с функциями по п. 5.1, в т.ч. **ПолучитьПутьPing** для формирования пути GET ping по стране/типу продукции.
3. В **ОчередьОбменаМаркировкиСервер** перед основным запросом к API вызывать проверку доступности (GET ping по URL из ПолучитьПутьPing + параметры; при неуспехе основной запрос не выполнять).
4. Реализовать для **Казахстан**: ПолучитьПутьPing, ФормироватьТелоЗапросаЗаказКодов, ПолучитьПутьAPIЗаказКодов, РазобратьОтветЗаказКодов (с учётом omsId и clientToken по документации СУЗ).
5. Реализовать для **Узбекистан** то же (ping — по документации оператора).
6. В документе **ЗаказКодовМаркировки** (кнопка/проведение) вызывать формирование тела через ФорматыAPIМаркировкиСервер и ДобавитьВОчередь.
7. В **ОчередьОбменаМаркировкиСервер** подставлять путь API через ПолучитьПутьAPIЗаказКодов и в СоздатьПоступлениеКодов вызывать РазобратьОтветЗаказКодов с заполнением документа.
8. Проверить проведение **ПоступлениеКодовМаркировки**: записи регистра **КодыМаркировки** создаются, данные соответствуют заказу и ответу API.

После Этапа 5 переходят к Этапу 6 (выгрузка кодов для станции, загрузка JSON результата станции) и далее по плану.
