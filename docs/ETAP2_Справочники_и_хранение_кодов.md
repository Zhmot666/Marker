# Этап 2: Справочники и хранение кодов маркировки

Документ описывает метаданные Этапа 2: номенклатура с типом продукции (ЛС/БАД), клиенты для заказов, справочник типов продукции и перечисление статусов кодов, структура хранения кодов маркировки (в т.ч. бинарное хранение ответов API).

---

## 1. Справочник «ТипыПродукцииМаркировки»

Типы продукции для маркировки (ЛС, БАД; в части стран маркируются и БАДы). Справочник используется вместо перечисления, чтобы при необходимости добавлять новые типы без изменения конфигурации.

| Реквизит | Тип | Назначение |
|----------|-----|------------|
| Наименование | Строка | Наименование типа (например, «Лекарственное средство», «Биологически активная добавка») |
| Код | Строка, необязательно | Код типа для обмена с API (например, ЛС, БАД) |
| ОбозначениеТоварнойГруппы | Строка, необязательно | Обозначение товарной группы для подстановки в URL API (например, `pharma` для ЛС). Используется в шаблонах вида `…/api/v2/{{extension}}/aggregation?…`, где вместо {{extension}} подставляется это значение |
| ПометкаУдаления | Булево | Стандартный реквизит |

**Предполагаемые элементы справочника:** ЛС (код «ЛС», наименование «Лекарственное средство», обозначение товарной группы «pharma»), БАД (код «БАД», наименование «Биологически активная добавка», обозначение — по документации API страны). При необходимости добавляются другие типы.

Используется в справочнике «Номенклатура», в документах заказа и заказа кодов.

---

## 2. Справочник «Номенклатура»

Номенклатура продукции, участвующей в маркировке. Основа для строк заказа и заказа кодов.

| Реквизит | Тип | Назначение |
|----------|-----|------------|
| Наименование | Строка | Наименование позиции |
| ТипПродукции | СправочникСсылка.ТипыПродукцииМаркировки | Тип продукции (ЛС, БАД и т.д.) |
| GTIN | Строка (13) | Глобальный идентификатор товара (GTIN), 13 символов. **Важно** для формирования запросов и отчётов в API маркировки |
| Код | Строка, необязательно | Дополнительный внешний код для обмена с API при необходимости |
| ПометкаУдаления | Булево | Стандартный реквизит |

При необходимости позже можно добавить реквизиты для привязки к стране (например, «УчаствуетВМаркировкеКЗ», «УчаствуетВМаркировкеРФ» и т.д.) или общий флаг «УчаствуетВМаркировке» с учётом функциональных опций по странам.

**Вид справочника:** иерархия при необходимости (группы/номенклатура); иначе плоский список.

---

## 3. Справочник «Контрагенты»

Контрагенты, на которых формируются заказы (использует роль «МенеджерМаркировки»).

| Реквизит | Тип | Назначение |
|----------|-----|------------|
| Наименование | Строка | Наименование контрагента |
| Страна | ПеречислениеСсылка.Страны | Страна (Казахстан, Узбекистан, Россия, Беларусь) для привязки заказов и отчётов к оператору маркировки |
| ИНН / Код | Строка, необязательно | Идентификатор для отчётов/API при необходимости |
| ПометкаУдаления | Булево | Стандартный реквизит |

---

## 4. Перечисление «СтатусКодаМаркировки»

Статус кода маркировки в системе (наличие, выдача на производство, использование).

| Имя значения | Синоним |
|--------------|---------|
| ВНаличии | В наличии |
| ВыданНаПроизводство | Выдан на производство |
| Использован | Использован (нанесён/учтён в отчёте) |

---

## 5. Хранение кодов маркировки и бинарных ответов API

Коды, полученные от API, и бинарные ответы хранятся так, чтобы можно было выгружать данные без потерь (в т.ч. при непечатных символах в GS1 DataMatrix).

### 5.1. Регистр сведений «КодыМаркировки»

Один ресурс — один код маркировки (одна запись = один код, например один DataMatrix).

**Измерения:**

| Измерение | Тип | Назначение |
|-----------|-----|------------|
| Номенклатура | СправочникСсылка.Номенклатура | Позиция номенклатуры |
| Заказ | ДокументСсылка.Заказ | Заказ, под который получен код (документ создаётся на Этапе 3) |
| НомерСтроки | Число | Номер строки заказа (1, 2, …) для привязки к строке |
| Оператор | СправочникСсылка.ОператорыМаркировки | Оператор (страна/сервер), от которого получен код |
| ДокументПоступления | ДокументСсылка.ПоступлениеКодовМаркировки | Документ поступления кодов (см. ниже), в котором зафиксирован приход |

**Ресурсы:**

| Ресурс | Тип | Назначение |
|--------|-----|------------|
| КодТекстовый | Строка, необязательно | Текстовое представление кода для поиска/отображения (может быть неполным при непечатных символах) |
| Статус | ПеречислениеСсылка.СтатусКодаМаркировки | ВНаличии / ВыданНаПроизводство / Использован |
| НомерВОтвете | Число, необязательно | Порядковый номер кода в бинарном ответе API (для извлечения из бинарника при выгрузке) |

Периодичность регистра: по дате поступления или без периодичности (в зависимости от того, нужна ли история по датам). Рекомендуется **непериодический** регистр, дата поступления при необходимости хранится в документе «Поступление кодов маркировки».

### 5.2. Документ «Поступление кодов маркировки»

Фиксирует факт получения кодов от API. Хранит бинарный ответ целиком, чтобы при выгрузке не терять непечатные символы.

**Реквизиты шапки:**

| Реквизит | Тип | Назначение |
|----------|-----|------------|
| Дата | Дата | Дата и время поступления |
| Оператор | СправочникСсылка.ОператорыМаркировки | Оператор (сервер), от которого получены коды |
| ЗаказКодов | ДокументСсылка.ЗаказКодовМаркировки | Ссылка на заказ кодов (документ Этапа 3), по которому получен ответ |
| ОтветAPIБинарный | ХранилищеЗначения | Тело ответа API в бинарном виде (полностью) |
| КоличествоКодов | Число | Количество полученных кодов (для контроля) |

**Табличная часть «Коды» (при необходимости детализации по строкам заказа):**

| Реквизит | Тип | Назначение |
|----------|-----|------------|
| Номенклатура | СправочникСсылка.Номенклатура | Номенклатура |
| НомерСтрокиЗаказа | Число | Номер строки заказа (если привязка к заказу известна на момент поступления) |
| Количество | Число | Количество кодов в этой строке |
| СмещениеВОтвете | Число, необязательно | Смещение в бинарном ответе для извлечения фрагмента кодов (при фиксированном формате ответа) |

При проведении документа «Поступление кодов маркировки» выполняется разбор ответа API (из бинарного поля или из разбора JSON в памяти), создаются записи регистра сведений **КодыМаркировки** с привязкой к документу поступления, номенклатуре, заказу/строке, оператору; при этом в регистр можно записывать **НомерВОтвете** для последующего извлечения кода из **ОтветAPIБинарный** при выгрузке на станцию.

**Альтернатива:** не заводить табличную часть в документе поступления, а формировать движения по регистру **КодыМаркировки** только из разбора бинарного/JSON-ответа в модуле проведения (номенклатура и привязка к строкам заказа приходят из контекста заказа кодов).

### 5.3. Связь «код — бинарный ответ»

- В регистре **КодыМаркировки** каждая запись связана с **ДокументПоступления**. В документе поступления хранится **ОтветAPIБинарный**.
- При выгрузке кодов для станции маркировки: для каждой записи регистра при необходимости можно прочитать бинарный ответ из документа поступления и извлечь фрагмент с кодом по **НомерВОтвете** или по смещению/длине (формат уточняется по API оператора), чтобы выгрузить код без перекодирования.

## 6. Порядок создания (Этап 2)

1. Создать справочник **ТипыПродукцииМаркировки** (Наименование, Код, ОбозначениеТоварнойГруппы), заполнить элементами ЛС и БАД (для ЛС — ОбозначениеТоварнойГруппы = «pharma» и т.д. по документации API).
2. Создать перечисление **СтатусКодаМаркировки** (ВНаличии, ВыданНаПроизводство, Использован).
3. Создать справочник **Номенклатура** с реквизитами Наименование, ТипПродукции, GTIN (Строка, 13), при необходимости Код.
4. Создать справочник **Контрагенты** (Наименование, Страна, ИНН/Код).
5. Создать регистр сведений **КодыМаркировки** (измерения и ресурсы по п. 5.1). Тип регистра — непериодический (или с периодом по дате поступления — на выбор).
6. Создать документ **ПоступлениеКодовМаркировки** с реквизитами шапки по п. 5.2 и при необходимости табличной частью; в модуле проведения — формирование записей регистра **КодыМаркировки** (логику разбора ответа API и заполнения регистра реализовать на Этапе 4–5 при подключении конкретного оператора).

После выполнения Этапа 2 можно переходить к Этапу 3 (документы «Заказ», «ЗаказКодовМаркировки», проведение «ПоступлениеКодовМаркировки») с использованием созданных справочников и регистра.

---

## Зависимости от Этапа 3

Регистр **КодыМаркировки** и документ **ПоступлениеКодовМаркировки** ссылаются на документы **Заказ** и **ЗаказКодовМаркировки**. Эти документы создаются на Этапе 3; при создании регистра и документа поступления в EDT временно можно задать тип ссылки «ДокументСсылка» с именем документа-заглушки или отложить создание регистра до появления документов заказа.
